# 电网仓（输入 / 输出）实现说明

> 目标：把 PrismPlan 里那套「直接从 ME 网络抽电 / 往 ME 网络送电」的能量仓，按 AE2 Supergiant 1.0.16 的新 API
> 在 ApplyGray 里重写一整套（输入 + 输出，2A/4A/16A/64A）。

## 2. 旧实现为什么不能直接搬过来

PrismPlan 的 `MetaTileEntityMEEnergyHatch` 依赖的是 AE2 1.0.x 的老能量 API，Supergiant 里这几处都变了：

| PrismPlan（旧） | Supergiant（新） | 说明 |
|---|---|---|
| `tile implements IAEPowerStorage` | `node.addService(IAEPowerStorage.class, this)` | 能量存储现在是**节点服务**，`EnergyService.addNode` 只认 `node.getService(IAEPowerStorage.class)` |
| `IEnergyGrid` / `getProxy().getEnergy()` | `IGrid.getEnergyService()` → `IEnergyService` | 服务改名，注入仍是 `injectPower(amt, mode)` |
| `new MENetworkPowerStorage(this, REQUEST_POWER)` | `IEnergyService.extractAEPower(amt, mode, PowerMultiplier)` | 旧版「请求供电」事件被删除；拉电改为直接调用能量服务 |
| `AENetworkProxy` + 手写 `createProxy()` | `GridHelper.createManagedNode(owner, listener)` → `IManagedGridNode` | 节点生命周期由 `IAEManagedMetaTileEntity` + `MixinMetaTileEntityHolder` 托管（create / load / save / destroy） |
| `AEPartLocation` / `DimensionalCoord` | `EnumFacing` | 节点朝向、线缆连接判定都用 `EnumFacing` |
| `IAEPowerStorage` 无事件义务 | 值变化必须发 `GridPowerStorageChanged(VALUES_CHANGED)` | 新能量服务缓存每个来源的贡献值，不发事件就会读到旧数 |

还有一条不属于 API、但同样致命的**契约语义**：新版 `IAEPowerStorage` 的 `getPowerFlow() = WRITE`（只让自己被充能）
并不会把网络里已有的电「推」到这个存储里 —— 网络没有自动均衡。所以旧实现里「挂个 WRITE 存储 + 发请求事件」的拉电
方式，在新版只能靠请求事件，而事件已经没了。

## 3. 本实现的方案

**双向都用「每 tick 主动 push / pull」，不注册自己的 `IAEPowerStorage`。**

- 输入仓（`isExportHatch == false`）：`energyService.extractAEPower(EU 预算 × 换算比, MODULATE)` → 转成 EU 存进
  GT 能量容器。
- 输出仓（`isExportHatch == true`）：把容器里的 EU 换算成 AE，`energyService.injectPower(..., MODULATE)`。

这样做的好处：

1. 不碰新版的存储服务契约 —— 网络的总量、路由缓存、`GridPowerStorageChanged` 事件全部由 AE2 自己维护，本模组没有
   会失效的缓存，也不需要在 GT 容器变化时补发事件。
2. 输出仓可以在**网络没电**时给网络充电：传输门槛只看 `node.getGrid() != null`，不看 `isActive()`
   （`isActive()` 要求网络已供电，正是旧实现踩过的死锁）。
3. 节点 `setIdlePowerUsage(0)` 且**不设** `GridFlags.REQUIRE_CHANNEL`：电网仓是能量通道而不是频道设备，它不应该为了
   工作而向网络要电、也不该占频道（AE2 自己的能量接收器 / 能量元件同样不占频道）。

### 换算比

`PowerUnit.EU.convertTo(PowerUnit.AE, 1.0)`，即跟随 AE2 自己的 EU 换算系数（当前 4.0，即 1 EU = 4 AE）。
没有在代码里写死第二个比例，整包调整 AE2 换算时电网仓自动跟随，工具提示里的数值也是同一来源。

### 取整策略

AE 是 `double`、GT 是 `long`。为了让「扣掉的 EU」和「搬动的 AE」严格对应，每 tick：

1. 先 `SIMULATE` 一次，算出网络**实际**能吃/能给多少 AE；
2. 向下取整成**整数 EU**，再按 `EU × 比值`（比值的整数倍）`MODULATE` 一次；
3. 用真实返回值再取整一次作为计费量。

因此既不会「多提了 AE 但 EU 被截断丢掉」，也不会「多注入了 AE 但 EU 没扣」（凭空造电）。没有跨 tick 的小数余量字段。

### 交互

| 操作 | 行为 |
|---|---|
| 软锤右击 | 暂停 / 恢复传输（`IControllable` → `CAPABILITY_CONTROLLABLE`，GT 的软锤逻辑直接生效） |
| 剪线钳右击 | 在「仅正面连接 AE 线缆」与「所有面都可连接」之间切换（与 GT 的 ME 仓一致，消息复用 GT 的 lang key） |
| TOP | 通过 `IAEStatusProvider` 显示 `ME 网络：在线 / 离线`（在线 = 已接入网络） |

## 4. 注册

- 类：`MetaTileEntityMEGridEnergyHatch`，继承 GT 的 `MetaTileEntityEnergyHatch`，因此方块能力（`IEnergyContainer`、
  多方块能力注册、电压/电流 tooltip、雨中爆炸等）与普通能量仓完全一致。
- 数组：`GRID_ENERGY_INPUT_HATCH[_4A|_16A|_64A]`、`GRID_ENERGY_OUTPUT_HATCH[_4A|_16A|_64A]`。
- ID：**250–353**，8 组 × 13 档（`GRID_HATCH_TIERS = GTValues.UXV + 1`）。
  每档 `id = 250 + 组序号 × 13 + tier`，组序号顺序为
  `输入2A / 输出2A / 输入4A / 输出4A / 输入16A / 输出16A / 输入64A / 输出64A`。
- 注册上限：常规 `ULV..UHV`（10 档，与 GT 自带能量仓一致）；`GregTechAPI.isHighTier()` 时扩到 `ULV..UXV`（13 档）。
  **上限只影响注册数量，不影响任何 ID**，切换 high-tier 模式不会挪号（未注册的档位号被保留）。
- 物品 ID：`applygray:me_grid_energy_hatch.input.<tier>`、`...input_4a.<tier>`、`...output_64a.<tier>` 等。
- 创造模式标签：沿用 `MetaTileEntity#getSubItems`，每台机器各自出现在标签里（与 GT 自带多台能量仓一致）。

## 6. 本次没做的部分

- **没有配方**：与 PrismPlan 的电网仓一致，目前只从创造模式标签获取。若要进生存，建议按档位注册
  `ASSEMBLER_RECIPES`（GT 对应档位能量仓 + AE 接口 / 加速卡），一次 80 条，需要单独设计材料梯度。
- **没有 GUI**：GT 能量仓本身右键无界面；状态通过 TOP + 物品提示给出。
- **没有把 EU 直接暴露成网络储能**（即把输入/输出仓做成 `IAEPowerStorage` 让 AE 把 GT 电池算进「网络储电量」）：
  那会引入值和路由事件的维护义务，且对「每 tick 传输一次」的行为没有帮助；如确有需要，应作为独立模式实现并补齐
  `GridPowerStorageChanged` 发送。
- **没有 256A / substation 变体**：如需，直接复用同一个类并新增一组数组与 ID 段即可。
