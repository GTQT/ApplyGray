### B. `f28e7f176` — 2026-07-28 — `Made some breaking changes to MEStorageMonitor…`　【2 个错误】

`ae2.api.storage.IStorageMounts` 的挂载入口收紧了类型：

```java
// 旧
default void mount(MEStorage inventory) { … }
void mount(MEStorage inventory, int priority);
// 新
default void mount(MEStorageMonitor inventory) { … }
void mount(MEStorageMonitor inventory, int priority);
```

（该接口最早在 `9983fa0bd` 2026-07-18 `add event-driven incremental storage updates (#71)` 引入 `MEStorageMonitor`，`f28e7f176` 把 `mount` 的参数改成只能收 `MEStorageMonitor`。）

**受影响文件：** `../src/main/java/applygray/common/metatileentities/multiblock/storage/MetaTileEntityQuantumAccessHatch.java` L109 / L111。

**修复方案：** 让内部的 `ItemStorageView` / `FluidStorageView` 实现 `ae2.api.storage.MEStorageMonitor`（它继承 `MEStorage`，只需再补两个方法）：

```java
@Override public void addListener(MEStorageChangeListener listener, Object verificationToken) { … }
@Override public void removeListener(MEStorageChangeListener listener) { … }
```

契约要求（`MEStorageChangeListener` 的 javadoc 明确规定）：
- 注册时若同一 listener 已注册，抛 `IllegalStateException`；
- `removeListener` 返回后，不得再对该 listener 回调；
- 回调必须与注册同线程（服务端线程）同步发生；
- 每次内容变化**恰好上报一次**有符号增量 `onStackChange(AEKey, long delta)`（正=增加，负=减少，0 无效）；
- 只有「无法用精确增量表达的结构性变化」才调 `onListUpdate()`，不得拿它代替普通变化。

**可参照的 AE2 原生实现：** `ae2.me.storage.DriveWatcher`、`ae2.tile.storage.TileMEChest` 的 cellHandler、`ae2.parts.storagebus.StorageBusPart`、`ae2.me.storage.CompositeStorage`。

> 换句话说：`ItemStorageView` / `FluidStorageView` 现状只是「一个可读可写的 `MEStorage`」。新版 AE2 不再轮询挂载存储，必须由被挂载方**主动推送增量**，否则量子存储单元接进 ME 网络后内容变化不会被网络感知 —— 这是功能性问题，不只是签名问题。

## 3. 运行期 mixin 破坏（javac **不会**报，只在启动/使用时炸）

### C. `223b040df` — 2026-08-16 — `Crafting calculation optimization (#88)`

> 该提交把合成计算改成图（`ae2.crafting.graph`）优先 + 传统树兜底，`CraftingCalculation` 与 `CraftingTreeNode` 内部几乎重写。

**C-1　`AccessorCraftingCalculation`（`@Invoker` 签名不匹配）**

目标方法由
`Collection<IPatternDetails> getCraftingFor(AEKey)`（包私有）
变为
`public ObjectList<IPatternDetails> getCraftingFor(AEKey)`。

`@Invoker` 要求 handler 的返回类型与被调用方法一致，故
`../src/main/java/applygray/mixins/supergiant/AccessorCraftingCalculation.java` L16 必须改为：

```java
@Invoker("getCraftingFor")
it.unimi.dsi.fastutil.objects.ObjectList<IPatternDetails> applygray$getCraftingFor(AEKey target);
```

**C-2　`AccessorCraftingTreeNode`（`@Accessor` 字段类型不匹配）**

字段声明由
`private List<CraftingTreeProcess> nodes = null;`
变为
`private ObjectArrayList<CraftingTreeProcess> nodes = null;`

故 `../src/main/java/applygray/mixins/supergiant/AccessorCraftingTreeNode.java` L17 必须改为：

```java
@Accessor("nodes")
it.unimi.dsi.fastutil.objects.ObjectArrayList<CraftingTreeProcess> applygray$getChildProcesses();
```

（调用方 `MixinCraftingTreeNodeLargePattern.applygray$collectInputCandidateDetails` 里用 `List<CraftingTreeProcess>` 接住仍然合法，无需改。）

**C-3　`MixinCraftingTreeNodeLargePattern` 的 `@Redirect` 描述符过期**

`../src/main/java/applygray/mixins/supergiant/MixinCraftingTreeNodeLargePattern.java` L77-78：

```
旧: target = "Lae2/crafting/CraftingCalculation;getCraftingFor(Lae2/api/stacks/AEKey;)Ljava/util/Collection;"
新: target = "Lae2/crafting/CraftingCalculation;getCraftingFor(Lae2/api/stacks/AEKey;)Lit/unimi/dsi/fastutil/objects/ObjectList;"
```

同时 handler 的返回类型必须跟着改成 `ObjectList<IPatternDetails>`（`@Redirect` 要求 handler 返回类型与目标指令返回类型一致），例如：

```java
@Redirect(method = "buildChildPatterns", at = @At(value = "INVOKE",
        target = "Lae2/crafting/CraftingCalculation;getCraftingFor(Lae2/api/stacks/AEKey;)Lit/unimi/dsi/fastutil/objects/ObjectList;"))
private ObjectList<IPatternDetails> applygray$expandLargePatternCandidates(CraftingCalculation calculation,
                                                                           AEKey target) {
    ObjectList<IPatternDetails> original =
            ((AccessorCraftingCalculation) calculation).applygray$getCraftingFor(target);
    Collection<IPatternDetails> expanded =
            DynamicRecipePatternRegistry.expandLargePatternCandidatesForCurrentSelection(this, target, original);
    return expanded instanceof ObjectList<IPatternDetails> list ? list : new ObjectArrayList<>(expanded);
}
```

（`DynamicRecipePatternRegistry.expandLargePatternCandidatesForCurrentSelection` 的签名保持 `Collection` 入参/返回即可，仅调用点适配。）

**C-4　`requestInner` 的注入点数量变了 —— 需要钉死 `ordinal`**

字节码实测：

| | `buildChildPatterns()` 在 `requestInner` 内的调用点 |
|---|---|
| 旧 jar | 1 处（字节码偏移 248） |
| 新 jar | **2 处**（偏移 **1** 和 **644**） |

L41-42 的
`@Inject(method = "requestInner", at = @At(value = "INVOKE", target = "…buildChildPatterns()V", shift = BEFORE))`
默认会在**两处都注入**，于是 `applygray$beginLargePatternSelection` 每次 `requestInner` 会被调用两次。

- `DynamicRecipePatternRegistry.beginLargePatternSelection` 只是 `ThreadLocal.set`，同参数重复调用幂等，**大概率不会产生错误结果**；
- 但语义确实变了：新版偏移 1 处位于方法开头，若随后在偏移 642 的 `return` 提前返回，第二处注入点不可达，选择作用域会一直挂着（由 `buildChildPatterns` HEAD 的 `clearStaleLargePatternSelection` 兜底，且只对**其他** node 生效）。

**建议：** 用 `ordinal = 1`（对应偏移 644 那处）把注入钉死到与旧版相同的位置，然后按 §6 做回归。若不钉死，请至少显式验证「早退路径 + 两次 begin」不会让 `ACTIVE_LARGE_PATTERN_SELECTION` 泄漏。

## 7. 顺带修掉的既有缺陷：两处 `@Redirect` 一直是死代码（**已确认 + 已修复**）

`../src/main/java/applygray/mixins/supergiant/MixinPatternProviderLogicSmartCopy.java`（`0de0b81` 2026-08-11 引入，此后未改）原有两处 `@Redirect`：

```java
@Redirect(method = "pushPattern", at = @At(value = "INVOKE",
        target = "Ljava/util/List;contains(Ljava/lang/Object;)Z"))
@Redirect(method = "canMergePatternPushBasic", at = @At(value = "INVOKE",
        target = "Ljava/util/List;contains(Ljava/lang/Object;)Z"))
```

而两个 jar（旧 `f55367e71` 与新 `1.0.16`）的 `PatternProviderLogic` 字节码里，这两处调用的 owner 都是
`it/unimi/dsi/fastutil/objects/ObjectList`（字段 `private final ObjectList<IPatternDetails> patterns`），
**不是** `java/util/List`：

```
新 jar  pushPattern               偏移 36: InterfaceMethod it/unimi/dsi/fastutil/objects/ObjectList.contains:(Ljava/lang/Object;)Z
新 jar  canMergePatternPushBasic  偏移 17: InterfaceMethod it/unimi/dsi/fastutil/objects/ObjectList.contains:(Ljava/lang/Object;)Z
旧 jar  同上两处，完全相同
```

**是否层级匹配？已从 Mixin 本体确认：不匹配。**
`org.spongepowered.asm.mixin.injection.struct.MemberInfo.matches(String owner, String name, String desc)` 的字节码是：

```
if (this.desc  != null && desc  != null && !this.desc.equals(desc))   return MatchResult.NONE;
if (this.owner != null && owner != null && !this.owner.equals(owner)) return MatchResult.NONE;   // ← 纯字符串比较
if (this.name  != null && name  != null) { ... EXACT_MATCH / MATCH ... }
```

owner 用的是 **`String.equals`，不做任何类层次解析**；而 `BeforeInvoke.find` 只接受 `match.isExactMatch()`。
→ `Ljava/util/List;` 这个 owner 永远不可能命中 `ObjectList.contains`，**这两个 redirect 从 2026-08-11 起就没生效过**。

**顺带确认了一个重要的 Mixin 语义（对本方案很关键）**：

> 该 mixin 自 2026-08-11 起就带着这两处永不匹配的 redirect，而作者一直在正常跑游戏 ——
> 说明本工程这套 Mixin 构建里，**注入点匹配数为 0 是「静默跳过」而不是「启动崩溃」**。
> 因此 §3 那几处描述符/签名改动即便改错，也不会崩，而是**功能悄悄失效**。
> 这正是为什么本方案坚持对每个 target 做字节码级逐一核对，而不是「编译过了就行」（见 §10 的全量核对表）。

**已修复**：owner 改为 `Lit/unimi/dsi/fastutil/objects/ObjectList;`，handler 的接收者参数由 `List<?>` 改为
`ObjectList<?>`（与指令上的实际类型完全一致，避免依赖 Mixin 是否允许父类型）。

> ⚠️ **这是一次行为变更，不只是改字符串**：修复后这两条路径**从未激活变为激活** ——
> 智能复制（smart copy）的连接目标侧，现在会真正接受来自源 Provider 的样板（`pushPattern` 的
> `!this.patterns.contains(basePatternDetails)` 与 `canMergePatternPushBasic` 的同名判断）。同 mixin 的
> `getAvailablePatterns` 注入（无 INVOKE target）一直是生效的，所以此前是「能对外宣称源样板、但推送时被拒」的半残状态。
> 若回归中发现智能复制的推送/合并行为异常，这两处就是第一嫌疑点。

### 10.1 为什么 §3 的四项用「静态复核」而不是「启动验证」

Mixin 的 accessor/invoker/redirect 校验发生在**目标类被加载时**（惰性）。
`CraftingCalculation` 只在真正跑合成计算时加载，`AEBaseGui`/`AbstractPatternAccessTerm` 只在客户端 GUI 打开时加载，
所以 `runServer`/`runClient` 启动都覆盖不到这几处；要用游戏验证就必须实际玩到那三块功能。
因此这里采用「对两个 jar 的字节码逐条比对 + 158 项单测」，可复现、无遗漏，见 §8。

## 11. 已知环境问题：本机 `gradlew test` 用不了（与本次改动无关）

**现象**：`gradlew test` 报每一个测试类 `java.lang.ClassNotFoundException: applygray.XXX`（含完全没被改过的类）。

**根因（已实测确认）**：

1. Gradle 用 `@argfile` 把 worker 的 classpath 传给测试 JVM：
   `java.exe ... @E:\.gradle\.tmp\gradle-worker-classpathXXXXtxt`
2. Gradle 把该文件写成 **UTF-8**；而该 JVM 的 `sun.jnu.encoding = GBK`（中文 Windows 区域设置），
   JDK 读 `@argfile` 用的是 **`sun.jnu.encoding` 而不是 `file.encoding`**。
3. 于是 `E:\模组开发\...` 被解码成 `E:\\妯＄粍寮€鍙慭\...` → 所有位于中文路径下的 classpath 条目失效 →
   `../build/classes/java/test` 找不到 → 每个测试类都 `ClassNotFoundException`。
   ASCII 路径（`E:\.gradle\...`、`C:\Users\...`）不受影响，所以编译、依赖解析都正常。

**实测证据**：

| 探针 | 结果 |
|---|---|
| `java -cp "build\classes\java\test" applygray.LocalizationResourceTest`（直接命令行） | 类**加载成功**（报缺依赖 `NoClassDefFoundError`，非 ClassNotFound） |
| 同样内容写进 `@argfile`（UTF-8） | `ClassNotFoundException` |
| 同样内容写进 `@argfile`（GBK） | 类**加载成功** |
| `java -XshowSettings:properties` | `file.encoding=UTF-8`，`native.encoding=GBK`，`sun.jnu.encoding=GBK` |

**可选规避（任选其一）**：

- 把工程放到**纯 ASCII 路径**（如 `E:\moddev\GTQT\ApplyGray`）——最可靠；
- 打开 Windows「区域设置 → 管理 → 更改系统区域设置 → **Beta: 使用 UTF-8 提供全球语言支持**」，
  让 `sun.jnu.encoding` 变成 UTF-8；
- 临时绕过（本次就是这么跑出 158/158 的）：自己写一个 JUnit Platform 启动器，
  用**直接命令行 `-cp`**（不经过 `@argfile`）运行，或在 `@argfile` 里写 **正斜杠** 且用 GBK 编码。

> 注意：`-Dfile.encoding=UTF-8`（含 `JAVA_TOOL_OPTIONS`）**无效**，因为 argfile 读的是 `sun.jnu.encoding`，无法用 `-D` 覆盖。这条也排除了「在 gradle.properties 里加参数」这种工程内修法。
>
> `runClient` / `runServer` 不受影响（Gradle 的 JavaExec 走 manifest `Class-Path`，是 ASCII 百分号编码，Java 解码正常）。
